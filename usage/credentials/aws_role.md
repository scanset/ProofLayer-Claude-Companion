# `aws_role`

AWS IAM role assumed via STS from a source identity. The canonical
"third-party scanner" pattern for AWS — the customer creates a role
Prooflayer assumes, optionally requiring an external ID for confused-
deputy mitigation.

## What it represents

A role that gets assumed at scan time. The actual auth material is
ephemeral (15-min default STS session), regenerated by the SDK on
every call. The credential payload just describes which role to
assume and how to find the source identity.

## Payload fields

| Field            | Required | Description                                                                |
|---               |---       |---                                                                         |
| `role_arn`       | yes      | Full ARN of the IAM role to assume                                          |
| `external_id`    | no       | External id required by the role's trust policy (confused-deputy protection) |
| `source_profile` | no       | Named profile in the AWS CLI config to chain from (rare in production)      |

## Metadata fields (non-secret, operator-set)

| Key                  | Purpose                                                                                                              |
|---                   |---                                                                                                                   |
| `region`             | Default AWS region for SDK calls                                                                                      |
| `account_id`         | The target account (the customer account, not Prooflayer's)                                                          |
| `credential_source`  | How the source identity is discovered. `Ec2InstanceMetadata` (default, prod VM with instance role), `Environment` (laptop with `AWS_PROFILE` / `AWS_ACCESS_KEY_ID` already set), or `EcsContainer`. |

## How to provision

In the **customer** AWS account (the one being scanned):

```bash
# 1. Define the trust policy — who can assume this role
cat > prooflayer-trust.json <<EOF
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::<prooflayer-aws-account>:role/prooflayer-source-identity" },
    "Action": "sts:AssumeRole",
    "Condition": {
      "StringEquals": { "sts:ExternalId": "scanset-2026-q2-xyz" }
    }
  }]
}
EOF

# 2. Create the role with that trust policy
aws iam create-role --role-name prooflayer-scanner \
  --assume-role-policy-document file://prooflayer-trust.json

# 3. Grant least-privilege read perms (start with ReadOnlyAccess)
aws iam attach-role-policy --role-name prooflayer-scanner \
  --policy-arn arn:aws:iam::aws:policy/ReadOnlyAccess

# Output the ARN — paste this into Prooflayer
aws iam get-role --role-name prooflayer-scanner --query Role.Arn
# → arn:aws:iam::123456789012:role/prooflayer-scanner
```

On **Prooflayer's** AWS account, ensure the source identity exists:
- VM has an instance profile with `sts:AssumeRole` permission against
  the customer's role ARN (use `credential_source = Ec2InstanceMetadata`)
- OR an `aws_access_key` credential exists in the env (use
  `credential_source = Environment`)

## How to add in Prooflayer

System-UI → **Admin** → **Credentials** → **Add credential**:

1. **Name**: descriptive (e.g. `customer-acme-prod`)
2. **Kind**: AWS role (assume)
3. **Role ARN**: paste `arn:aws:iam::…:role/prooflayer-scanner`
4. **External ID**: paste whatever the trust policy expects
5. **Metadata**: set `region`, `account_id`, `credential_source`
   (defaults to `Ec2InstanceMetadata`)

## Used by

- AWS Resource Explorer discovery
- AWS SSM channel for host-mode scans

> **Not for EKS.** EKS cluster discovery + container scanning need a
> self-contained identity Prooflayer can present directly — use
> [`aws_access_key`](aws_access_key.md) (see its EKS section). A role isn't
> usable there yet: the in-process apiserver-connection path has no ambient
> source identity to assume from (instance-profile source isn't supported on
> that path yet).

## Rotation

The STS session itself auto-rotates per call (no manual rotation).
What you rotate when:

- **External ID**: per audit-engagement rollover. Update the customer's
  trust policy and the Prooflayer credential's `external_id` field
- **Source identity** (the AWS access key behind the assumption): per
  the `aws_access_key` doc's rotation guidance
- **Role policy**: when the customer changes scope, no Prooflayer
  credential change needed

## Failure modes

| Symptom                                                              | Likely cause                                                                       |
|---                                                                   |---                                                                                 |
| `AccessDenied: Not authorized to perform sts:AssumeRole`             | Source identity isn't in the trust policy's Principal or external_id doesn't match |
| `AccessDenied: User is not authorized to perform <action>`           | Role's attached policies are too narrow                                            |
| `Unable to locate credentials`                                       | `credential_source = Environment` set but no `AWS_*` env vars present              |
| `Could not connect to the endpoint URL` from SDK                     | `region` metadata missing or wrong                                                  |

## Security notes

- External IDs are confused-deputy protection. Always set one for any
  cross-account scan, even single-customer scenarios.
- The source identity's `sts:AssumeRole` permission should be scoped
  to specific target role ARNs, not `*`.
- For 3PAO workflows: rotate external IDs per engagement so a
  previously-granted role can't be re-assumed after engagement end.
